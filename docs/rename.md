# Jarvis → Persona: compatibility migration

## Identities that do not change

The product is called **Persona** everywhere, and the new server entry point is `personad`; the old `jarvisd` command, build entry points, and release artifacts keep working. The rename is not a reinstall. These stay as they are: existing Bundle IDs / applicationId, App Store records, APNs and Keychain / App Group identities, database accounts and database names, Docker project and volume names, existing service-manager unit identities, and the public install and relay addresses. Do not rebuild the database, re-pair phones, or register a second App because of the rename.

The avatar still uses the existing `persona` data model and the `personas/` directory; existing avatar IDs do not change. Product entry points use full names such as `PersonaApp` so they are not confused with the avatar model.

## Run directory: one store, two entry points

Runtime data is accessed through `~/.persona` by default; `~/.jarvis` stays compatible. Starting the hub / node and the installer only create a missing directory alias. They never copy recursively, move an existing directory, or overwrite an existing symlink.

- Only the old directory exists: keep it in place and attach it via `~/.persona → .jarvis`; existing Claude / Codex session directories, skills, and cache paths do not change.
- Fresh install: also uses `~/.persona → .jarvis`, with the real directory still `.jarvis`. This compatibility layout is deliberate: old versions of the assistant identify sessions by working directory, and keeping the physical path lets a rollback after a fresh install work too, not just let both sides find the files.
- Only an existing new directory: keep it and create `~/.jarvis → .persona`. The user's own data is not moved.
- Both entry points already point to the same directory: return the new entry point first. Querying the socket alone never writes directories. Before installing a package, the SDK runs the same initialization as Go / the installer, so a recursive mkdir cannot get in first and turn the new path into a second store. On a race while creating the alias, verify that both sides are the same object; seeing EEXIST alone is not success.
- The file system does not support symlinks, or the user's HOME does not allow creating a new alias: if the original directory exists and is usable, keep using the original store; a failed helper alias must not take an old deployment down. The installer's command alias can degrade to a thin forwarding script. Permission changes, loops, and unusable targets still report errors and never create a separate empty store.
- Two independent directories both have content: never merge automatically or overwrite. The default keeps using the old store, so an old deployment does not silently switch to a different token / machine UID / knowledge base on upgrade. To really use the other one, set `PERSONA_HOME` explicitly.
- The symlink points to an external directory: if the target exists, use it in place; if the target is unusable, refuse to start a new store and restore the target first. A one-way dangling symlink between the new and old default names can have its target filled in; a symlink loop cannot.

`PERSONA_HOME` (compatible with `JARVIS_HOME`) sets the run root. It can be an absolute path, `~/…`, or a path relative to that user's HOME. It is lexically normalized first, so with `..` in it the installer and Go / SDK cannot each interpret it differently via symlink paths. Different environments can each use their own root; a custom root does not change the symlink of the user's default directory. The node's `data_dir` is an optional machine info field; a new hub uses it for that machine's actual assistant directory, and falls back to the old default path when an old node does not report it. Both the new and old assistant directories are recognized as the assistant; an ordinary project named `assistant` does not count.

The node socket uses the shorter old path within the same store. Otherwise the one extra character in the new name could push an old HOME that was right at the Unix socket path length limit over it, and the node could not listen after upgrading. The new path still reaches the same socket through the directory alias.

Do not migrate by copying hub.json: the two sides' knowledge bases, machine UID, socket, update state, and encryption keys would gradually diverge. The database stays the original database, and the directory alias makes the token and `secret.key` the original files too.

## Deploy scripts recover the run directory per service

`scripts/persona_identity.py`, introduced by #773, only recovers the run identity; it does not read build config or hub.json. #837 completed HOME-only recovery from external environment files, merged as `62039ebc4d17285a4ffd39e3631e96e18e65c70d`. It extracts only `PERSONA_HOME` / `JARVIS_HOME`; other fields are not returned, not logged, and not used for authentication. Other settings without a HOME no longer block recovering the original default store just because the file exists. Deploy / test scripts pick the service with `--service hub`, `--service node`, or `--service link`, so that when the hub and the node / Link on the same machine use different roots, none borrows the wrong directory:

- When the environment explicitly defines `PERSONA_HOME` or `JARVIS_HOME`, use that environment directly. The new name wins, including an empty value; no root is borrowed from an installed service.
- systemd: read the matching old unit from `XDG_CONFIG_HOME/systemd/user` (`~/.config/systemd/user` when unset). hub checks only `jarvisd.service`; node checks `jarvisd-node.service` first, then `jarvis-link.service`; link checks in the opposite order. Without a systemd unit, node / link can query the original launchd plist for their role, without changing the unit identity.
- **When the old service exists but neither its unit nor its external environment files have a HOME, keep using the original default store.** Once a unit for the role is found, it never borrows the root of another role or a fallback service. An old service is never silently moved just because another service on the same machine has a custom root.
- It parses the main unit and `.d/*.conf` sorted by file name, supporting `Environment=` empty resets, later overrides, line continuation, and `%h` / `%%`. Only `PERSONA_HOME` / `JARVIS_HOME` are kept; no other environment values are extracted. In auto mode, different independent roots are refused and a specific service must be chosen; two roots that SameFile confirms point to the same default store are not reported as a conflict.
- `EnvironmentFile=` supports in-order overrides of same-named unit environment, the `-` prefix for optional files, wildcards, and empty assignment to reset the file list; only the new and old HOME are extracted. No shell expansion is performed, and other fields are not returned or logged. `UnsetEnvironment=` removes matching variables after all files, and an empty assignment resets the removal list. A missing required file or a parse error in the root field stops it; an explicit HOME can name the real root directly, but failing to recover must never switch to a separate empty store.
- Queries create no directories by default; only `--prepare` initializes missing default aliases, keeping existing data, independent roots, and custom paths. `--prefix` combines the resolver with the given script for a remote host, which resolves and passes the new and old root variables remotely; the local root is never passed to the remote by mistake, and credentials are never expanded in the generated text.

## Environment variables

`PERSONA_*` is the new spelling; all existing `JARVIS_*` are still recognized. **When the new variable is defined, it wins, including an explicit empty value**, so an empty new token does not fall back to old credentials. Go code reads them all through `internal/identity`. Controlled variables passed to the assistant's MCP / plugin child processes are written under both names with duplicates removed, so an inherited old or new session ID cannot override this run's setting.

Build config prefers `PERSONA_CONFIG`, then `JARVIS_CONFIG`, defaulting to `~/.config/persona/config.json`; without the new file it reads the old `~/.config/jarvis/config.json`. When reading an existing default file it tries to fill in missing directory symlinks. When two existing config files coexist, the new one wins and the old one is not overwritten. A custom config file does not create a global alias.

The config script recomputes the derived exports (hub, bundle, team, and so on) from the selected config every time, exporting both names; it never treats values exported by a previous `env` as overrides, or switching environments in the same shell would still operate on the old deployment. For other runtime environment variables, it only bridges explicit `PERSONA_*` to the old name via a shell variable reference, without printing the value, and never invents a new-name override for a variable that only has the old name. Plugin tokens and the like never appear in the export script. The xcconfig keeps both the new and old build settings; signing and App identities in the config do not change.

The runtime SDK, DSH, and pi also recognize both the new and old socket / HOME environment variables. pi's new config file is named `persona.json`; without it, `jarvis.json` is still read. #773 added new-name-first reading of `PERSONA_PI_HOST` / `JARVIS_PI_HOST` and of the echo daemon's `PERSONA_DAEMON_TOKEN` / `JARVIS_DAEMON_TOKEN`. The App command CLI's bundle fallback prefers `PERSONA_BUNDLE_ID` and stays compatible with `JARVIS_BUNDLE_ID`; the existing `JARVISCTL_*` names, command arguments, and `~/.cache/jarvisctl` are kept, and no `PERSONACTL_*` set is invented because the tool was renamed. The runtime packages' old update IDs, session entries, and hot-reload state identities are kept, so installed plugins can receive new versions without reinstalling.

## Contracts, in phases

External names, source modules / types / directories, and storage compatibility land in separate PRs. Old URL schemes, HTTP headers, protocol fields, full MCP tool names, cache keys, and serialized type names are compatibility contracts and are never blindly string-replaced. New visible entry points can accept both new and old names; write formats that old Apps / old hubs must read keep the old representation until both sides have explicitly negotiated a new version.

When renaming source packages, take special care with Android serialization's default fully qualified class names, old notifications' ComponentName / PendingIntent, WorkManager's persisted Worker names, Swift rawValues, and archived caches. Renaming the source does not mean persisted names can change with it.

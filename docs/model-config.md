# 模型供应商与模型配置

## 两个入口各管什么

- **设置 › 模型供应商**：接入方式、API 协议、网关、加密凭据、默认模型，以及各台电脑已有的启动器。原来的「模型」页在这里，已有同步、隐藏、详情和额度能力保留。
- **设置 › 模型配置**：应用每种 AI 用途的供应商、具体模型、支持的思考强度。默认模型不等于所有用途必须共用的模型；在这里可以让分拣、对话、翻译等分别选择。

用途目录由 hub 提供，客户端不自己猜模型消费者。包含对话、AI 分身、飞书 `/agent`、新 Agent 默认、收件箱分拣与判断、手动草拟、翻译、知识处理及子用途、标题/标签名、定时任务及各真实任务；已接入的语音插件也可设置 Jarvis 默认模型。这里说的「技能」是应用内 AI 用途，不是接管每个 Claude Code 外部 Skill。

## 供应商与执行方式

| 执行方式 | 用在哪里 | 约束 |
| --- | --- | --- |
| 直接 API | 分拣、判断、翻译、草拟、知识处理、标题 | Messages 或 Responses；hub 自己读取/解封凭据 |
| 启动器 | Claude Code / Codex 对话和 Agent | 必须在执行机器上存在，具体模型由 CLI/app-server 真正接收 |
| 插件模型 | 已接入的语音服务 | 只能选择该插件提供的模型，不修改插件自己的供应商或凭据 |

原 `/launchers` API 保留。新增接入的 `kind` 是 `launcher` 或 `api`；旧条目省略时还是启动器。API-only 接入不下发给 node，也不放进新会话启动器列表。旧 `hub.json` 的 API 连接显示为兼容来源，认证文件路径和值不返回客户端。

## 编辑与继承

每项同时显示「当前生效」和「此用途的设置」：

- 供应商留空：继承；具体模型留空：使用该来源的默认模型。
- 更换供应商时清除旧的模型和思考强度，避免把不同供应商的字段拼在一起。
- 「恢复继承」只清除这一项的覆盖，按「保存」后生效。
- 供应商无法发现模型目录时可填合法模型 ID；保存不是付费可用性测试。
- 离线、协议不匹配、供应商缺失等状态明确显示，显式配置失效不会偷偷换一家供应商。
- 两台设备同时修改同一项时用 revision 检查；冲突保留草稿，需重新加载再保存。

API 类用途（分拣、判断、草拟、翻译、知识处理、标题）没有覆盖、旧 `hub.json` 的 `ai` 也没配时，自动用 hub 上能直接调用的接入：先找第一个 `kind: api` 的，再找第一个带 Key、Messages 协议的 Jarvis 管理启动器（隐藏的、缺地址 / 默认模型 / Key 的不算），模型用它的默认模型。「继承来源」显示「自动选择」，不写入覆盖，之后在这里选的照样优先。一个都没有时状态和报错都说清楚去哪配（#388，2026-11-02：只配了「Claude Code 默认」时草拟回复直接报 no model configured）。

「Claude Code 默认」这类启动器只是各台电脑上的 CLI，没有 API 地址和 Key，hub 不能直接调用，所以不会出现在 API 类用途的选项里。

首次打开不改变既有模型。旧基线仍保持原来的关系：分拣/判断各覆盖顶层 `ai`；翻译默认跟随分拣；有 `kb.ai` 时保持它原先的继承行为；AI 分身和 `/agent` 的旧专属启动器仍有效。统一用途覆盖优先于这些旧基线，业务消费者不再各自后置覆盖。

用途覆盖存 Postgres 的独立 settings 键，静态用途用数据库原子 revision 检查；任务模型复用真实任务字段，不复制任务。当前任务模型的版本检查和保存依赖单个 hub 的 schedule 锁，不支持多个 hub 进程并发修改同一份任务列表。助手/任务旧接口兼容统一来源。新客户端修改时间、提示词、权限时不发送旧模型字段，避免把在统一页刚保存的模型盖回去。

## 生效边界

- API 用途在下一次调用开始时解析配置；知识库使用按用途的可注入模型，不再固化 hub 启动时的旧对象。
- 对话和 Agent 的具体主模型走 CLI 参数或 Codex app-server model 字段，不只写可能被启动器清掉的环境变量。
- 预热/进程复用带执行指纹，同名启动器换了模型或凭据也不使用过期实例。
- 保存不杀当前轮次或后台任务。需要换进程而当前仍忙时拒绝切换，待安全边界再发起；不宣称 Claude/Codex 跨执行器无损续聊。
- 不重跑历史分拣、不重写已有知识。翻译缓存区分模型配置，下一次翻译不会误用旧配置的缓存。
- 新 Agent 默认「跟随模型配置」，手选启动器是本次覆盖，不再把客户端上次选的启动器自动盖在全局配置上。Claude Code 和 Codex 都保留各自的新建路径；Codex 新建需要首条消息，具体模型用明确的 `--model` 覆盖，思考强度仍由它自己的启动器管理，不把 Claude 的权限/思考参数混进去。
- 语音模型只在下一次语音会话开始/重新开始时读取。旧 hub 404 时可兼容读取旧客户端默认；新 hub 读取失败不能当作没有配置而回退。
- 模型变化不改变权限模式，也不授权自动发送消息。

## 接口

`GET /api/v1/model-config` 返回 `purposes` 与 `providers`；`GET /api/v1/model-config/purposes/{id}` 返回单项 `purpose` 与可用 `providers`。

`Purpose` 包含 `id/name/group/kind`、`override`、`effective`、`revision`、`inherited_from/status`，以及限定表单的 `fields/provider_ids`。动态任务为 `task.<任务 id>`，插件为 `plugin.<插件 id>`。响应不包含秘密。

单项保存：

```json
{
  "revision": 0,
  "provider": "launcher.<供应商名称>",
  "model": "<具体模型 ID>",
  "effort": null
}
```

发送至 `PATCH /api/v1/model-config/purposes/{id}`。缺失字段不变，`null` 清除覆盖，非空值覆盖；成功返回与 GET 单项相同的结构。仅支持该用途列出的字段；revision 不匹配返回 409，未知用途不会被临时创建。

## 验证

- 服务端使用真实 Postgres 验证存取、单项并发更新、旧配置兼容、每个消费入口的有效模型、缓存与执行器参数。
- Apple 用 `FakeHub` 测解码、PATCH 的 null 语义、草稿/冲突及普通任务保存不覆盖模型；UI 用 `ModelConfigurationTests` 和 DEBUG `-openModelConfiguration YES [-openModelPurpose <用途 id>]`。
- 网页和 Android 有相同协议的纯逻辑测试。
- `python3 -I scripts/test_model_config_mock.py` 启独立 mock，覆盖目录、保存、冲突、恢复继承与未知用途；不会调用真实模型。
